# Vendor city footprint evidence contract

The vendor city footprint is a **qualified view**: it separates confirmed identity links from
records that mention the vendor name while stating how much of the known source material is
represented. It does not treat an empty confirmed-link set as proof that no record exists.

The build writes the current machine-readable measurements to
[`vendor-footprint-coverage.json`](vendor-footprint-coverage.json). The receipt is regenerated by:

```bash
node tools/build_entity_intelligence.mjs
node tools/build_entity_intelligence.mjs --check
```

## Coverage shown to readers

The Awards section uses the full committed OCP Recent Contract Awards materialization as its
single all-row denominator. The full-corpus vendor profile aggregate applies the existing exact
`vendor_stem_v1` normalizer to every row; rows with a non-empty stem are published as strong
name-based award attachments. This aggregate is independent of the bounded cross-domain graph,
so a 500-row intake or 200-root graph cap cannot change the award census. Each vendor's exact
normalized stem still defines the set of distinct known award request IDs used by its profile
count and destination scope. When the identity graph has no confirmed links but the source has
records under the name, the reader sees:

> N records mention this name — identity not yet confirmed

Payments, land use, property, rules, meetings, and franchises/concessions do not yet have full
vendor-specific denominators. Their visible count includes confirmed and tentative
entity-intelligence records, while detailed rows remain confirmed-only. Review-only and unscored
candidates stay out. The interface says that completeness has not been measured instead of
presenting an unmeasured zero as a complete result.

The current denominator, numerator, source vintage, and excluded confidence bands live in the
JSON receipt rather than this prose so a rebuild cannot leave stale counts here. The receipt also
publishes observation survival through normalization, blocking, scoring, and publication, plus
the no-name floor. Missing vendor names remain excluded from vendor-specific profile rows; they
are retained in the all-row denominator.

## Promotion gates

The qualifier labels may be removed only when every gate below passes in the generated receipt:

| Gate | Threshold | Why it is required |
|---|---:|---|
| Award linkage | At least 95% of distinct known awards linked | Prevents a small linked slice from looking like the vendor's award history. |
| Multi-domain breadth | At least 50% of materialized vendor roots with records in two or more domains | Prevents an awards-only index from being presented as a citywide footprint. |
| Section denominators | 100% of the seven shipped sections have measured vendor-specific denominators | Prevents a populated section count from being mistaken for coverage. |
| Identity precision | At least 200 reviewed accepted links, no more than 1% confirmed false positives, and a full-corpus precision basis | Keeps broader coverage from being purchased with weaker identity claims. |

These are **standing bars**, not targets that can be waived by changing copy. When all four pass,
the build sets `qualifier_required` to `false`; the interface removes coverage qualifiers while
continuing to exclude tentative and review-only matches. Until then, every section retains either
its measured coverage sentence or an explicit unmeasured-coverage label.

## Daily read model and composition contract

`refreshVendorProfiles` attaches each vendor's footprint from the committed entity-intelligence
lookup and coverage index before publishing the versioned KV buckets. A profile request therefore
returns identity, recent notices, forecasts, and the footprint in one read; a missing footprint is
rendered as unavailable instead of starting a second profile-blocking request.

Destination links are built through `scopeWithEntity`, `intersectScopes`, and
`routeHashFromScope`. The same materialized query writes `result_count_receipt` into the versioned
scope. Money, Land, Property, Rules, and Meetings consume that receipt for their result label, so a
section cannot display zero while its destination displays records. Browser coverage exercises
this invariant in `test/functional/26_vendor_footprint_scope_count.py`.
