## Where should a new read get its data?

Build the resident answer from a CityScroll-owned snapshot. Use DuckDB and Parquet for bulk joins, KV for a bounded prepared answer, and D1 for durable records and queries. This keeps publisher outages off the normal read path. Publish the payload before promoting the key that readers follow, so a failed write leaves a usable version. Check departures against the [resident-read policy](https://github.com/cityscroll/cityscroll-app/blob/main/architecture/resident-read-policy.json). [Delivery model](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/static-first.md) · [Warehouse](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/duckdb-parquet.md) · [Storage choice](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/kv-vs-d1-search.md) · [Publication order](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/route-read-model-kv-publish.md).

Choose a lookup that bounds the work for a single request. Keyword search ranks up to 100 candidates per family in D1, then checks exact token evidence. Entity dossiers use keyed D1 reads. Organization search uses sharded static files so the complete index can stay out of the Worker bundle. Exercise the [organization search tests](https://github.com/cityscroll/cityscroll-app/blob/main/test/organization_search.test.mjs). ## When can two records be connected?

Start with publisher identities. A shared contract key can establish a relationship between two records while each keeps its own identity. Give the edge a type and provenance. Exact keys or reviewed evidence can establish identity. Inferred edges require the precision threshold for that relation. Contradictions block automatic matches. The [subject parser](https://github.com/cityscroll/cityscroll-app/blob/main/worker/src/lib/subject_registry.mjs) owns identifier kinds and the [ontology registry](https://github.com/cityscroll/cityscroll-app/blob/main/ontology/registry.v0.json) records which relationships have evidence. [Subject keys](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/subject-registry.md) · [Join keys](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/cross-domain-object-links.md) · [Review thresholds](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/entity-resolution-taxonomy.md) · [Publication rules](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/link-not-merge.md) · [Registry](https://github.com/cityscroll/cityscroll-app/blob/main/docs/adr/ontology-registry-v0.md).

## Goals and constraints

CityScroll makes New York City public records easier to follow by interest, place, agency, vendor, project, parcel, and civic process. The product currently presents contracts, staffing, zoning, property, rules, meetings, and related alerts. A record page should lead with plain meaning and a supported next action, while preserving the official source and the limits of what the source publishes. The [README](README.md) describes the public entry points and the main user journeys.

The main constraints are visible in the existing design:

- Public sources remain the source of truth. CityScroll may normalize, join, cache, and materialize them, but it must not silently turn an absent value into a fact. The source contract register in [`site/data/source_contracts.json`](site/data/source_contracts.json) and its generated view in [`docs/data-sources.md`](docs/data-sources.md) define the delivery and evidence boundary.
- Resident and required-CI reads are materialization-only. This is the standing invariant every surface is held to: browser routes, Pages handlers, public read endpoints, production builds, and required pull-request or merge gates read CityScroll-owned materializations and must not fetch publisher data at request or gate time. Scheduled or manual acquisition produces freshness; after acquisition failure, readers serve the latest-known-good materialization with its vintage or return a deterministic unavailable/not-found result. The canonical invariant is in [`docs/architecture.md`](docs/architecture.md#resident-read-invariant) and its gate is [`architecture/resident-read-policy.json`](architecture/resident-read-policy.json).
- The narrow exceptions are not civic-data reads: navigation to an official source-attribution URL; an explicitly invoked user transaction such as plain-English parsing, translation, subscription, or email delivery, provided the baseline civic record already came from a materialization and the transaction can fail without invalidating that record; and scheduled source acquisition, manually authenticated refreshes, or scheduled production/source-contract monitors that are not required pull-request or merge gates. None permits request-time publisher-data retrieval for a resident read, and none covers the migration departures recorded below.
- The site must remain useful when Worker-backed features are unavailable, and each seam fails separately. The static artifact and the edge-rendered documents that read only committed or built artifacts keep serving; alerts, feeds, natural-language search, forecasting, and the other server features degrade on their own. Useful is not the same as complete: the site-root Near You shell, `/near-you`, Following and preferences documents are Worker zone routes (Pages keeps a static Near You shell fallback for hosts without the apex route), and any document that hydrates from a Worker projection loses that layer. The concrete per-seam behavior is in [`worker/README.md`](worker/README.md).
- The [departure register](architecture/no-live-external-debt.json) lists each remaining call, owner and expiry. Run `node tools/no_live_external_reads.mjs --check` when changing a resident read.
- Identity joins are links, not merges. A source record keeps its publisher identity; cross-source links need a named rule, provenance, and the required confidence or review gate.

## System context

Visitors use the canonical CityScroll site in a browser. The static `site/` tree supplies markup, styles, committed data, and ordered browser-native modules. The route and module ownership map is [`docs/module-map.md`](docs/module-map.md). The browser reads committed or generated artifacts and calls the Worker for CityScroll-owned D1/KV projections, parameterized or stateful features, and explicit transactions; apart from the recorded notice-fallback debt above it does not query Socrata, geospatial, or other publisher data APIs for a resident read.

Requests to the canonical hostnames do not reach a static asset first. The Cloudflare Pages project runs an advanced-mode edge handler: [`site/_worker.js`](site/_worker.js) re-exports the default `fetch` in [`site/pages_edge.mjs`](site/pages_edge.mjs), which accepts only GET and HEAD, returns 503 without an `ASSETS` binding, server-renders a bounded set of canonical document routes — notices, meetings, procurements, rulemakings, regulatory-agenda items, mandates, matters, exams, committees, administrative-code sections, parcels, assertions, browse views, entity documents, monitor packs and district digests — and passes every other path through to `env.ASSETS`.

The Cloudflare Worker in `worker/` is the server boundary. Its public API host is `api.cityscroll.org`, with a second custom domain on the retired product domain kept as a compatibility alias; both hostnames are spelled out in the `routes` table of [`worker/wrangler.toml`](worker/wrangler.toml). Bounded reader routes also run on the canonical site for the site root (Near You shell as the default entry), Near You, Following, and preferences. The routes, domains, and three daily cron triggers are declared in [`worker/wrangler.toml`](worker/wrangler.toml) and inventoried, with each trigger's responsibility and the active or inactive state of every binding, in [`docs/release/cloudflare-native-builds.md`](docs/release/cloudflare-native-builds.md). The Worker handles notice ingest, search and translation caches, alerts, feeds, Checkbook projections and forecasts, entity views, operator routes, and the scheduled rebuilds described in [`docs/architecture.md`](docs/architecture.md).

Scheduled, manual-admin, and host-side acquisition consumes City Record and other NYC Open Data feeds, DCAS and Legistar data, Checkbook NYC, ZAP, GeoSearch, MapPLUTO, DOB data, and ABO datasets. Explicit transactions use Anthropic for the metered natural-language route and Resend for email, while Cloudflare supplies the serving platform. Each source has its own contract and acquisition or materialization path; those contracts do not authorize request-time publisher retrieval on a resident path. A source that is not published or not joined stays an explicit gap; the product does not infer the missing stage.

The main external outputs are the public site and record documents, saved-search feeds, email digests, public aggregate statistics, and bounded public entity and process views. Operator and spend views are keyed server routes. The system has no CLI product surface; deployment is through the site and Worker pipelines documented in [`docs/release/cloudflare-native-builds.md`](docs/release/cloudflare-native-builds.md), which separates what this repository configures from what only a provider dashboard can confirm.

## Building blocks

The repository is a modular monolith with separate browser, edge, and host-data seams:

- **Site.** `site/index.html`, `site/app/`, and pure `site/*.mjs` modules own browser presentation, route state, scopes, process timelines, actions, and progressive disclosure. `site/data/` holds committed read models and source-contract artifacts. The loader and module boundaries are recorded in [`docs/module-map.md`](docs/module-map.md).
- **Pages edge.** `site/_worker.js` re-exports `site/pages_edge.mjs`, the handler in front of the whole Pages project. It composes documents from static assets and Worker projections, so an edge document has two independent dependencies and two independent failure modes. It is a serving seam, not a data owner: it reads materializations and does not write any.
- **Worker.** `worker/src/worker.mjs` routes requests. Feature modules own ingest, notices, alerts, feeds, Checkbook, vendor and entity views, property and hearing projections, translations, usage, and scheduled work. The Worker uses Web APIs and does not open the warehouse on a request.
- **Cloudflare state.** The active production configuration has D1 `DB` (`crol-notices`) for the recent-notice mirror, FTS and durable workflow tables; KV `NL_METER` for metering; `ALERT_STATE` for digests, counters, forecasts, and versioned read models; `SUBS` for confirmed subscriptions and rate limits; and `FEEDBACK` for stored feedback and rate limits. Analytics Engine `USAGE_ANALYTICS` stores bounded aggregate events. Queue `DIGEST_QUEUE` fans out digest jobs to `crol-digests`, with a retrying consumer and dead-letter queue. Separate queue `DIGEST_SHADOW_QUEUE` carries authenticated post-repair shadow rebuilds to `crol-digest-shadow-rebuild`; D1 stores the run and per-digest checkpoints so retries resume without returning long work to the request path. These bindings are declared in [`worker/wrangler.toml`](worker/wrangler.toml).
- **R2 source vault.** The source-vault flag is `false` and the `SOURCE_VAULT` R2 binding is commented out in the current configuration. R2 is therefore a reserved, inactive seam, not a live dependency, and no source document is retained in object storage. Its current state is intentionally left null until the configuration and content-policy gates enable it. The configured-binding inventory is [`docs/release/cloudflare-native-builds.md`](docs/release/cloudflare-native-builds.md).
- **Warehouse.** `warehouse/` is the host-side factory for bulk public data and batch joins. Ingest writes gitignored raw files, Parquet tables, and a DuckDB catalog; small fixtures, manifests, and proof receipts are committed. Node seams query or export bounded rows, and builders turn them into JSON read models for `site/data/` and Worker twins. [`warehouse/README.md`](warehouse/README.md) documents the one-job, headroom-gated workflow.
- **Entity resolution.** [`entity_resolution/`](entity_resolution/) is an in-process package, not an HTTP microservice. It normalizes publisher values, generates candidates, scores them, applies conservative link or review policy, and publishes allowlisted public records. `cross_domain/` materializes provenance-bearing links across civic domains without merging publisher subjects. Its boundary and ADR links are in [`entity_resolution/README.md`](entity_resolution/README.md).
- **Ontology.** [`ontology/`](ontology/) is the backstage Civic Graph catalog and improvement flywheel. It registers civic objects, links, events, assertions, and actions with grounding states, then evaluates coverage, integrity, readability, and consistency. It is engineering infrastructure, not a public graph database or route. The registry decision is [`docs/adr/ontology-registry-v0.md`](docs/adr/ontology-registry-v0.md).
- **Community-board dual role.** Each community board is one stable civic body keyed by the publisher-backed `body_id` (`community-board:{borough-cb-NN}`). That identity boundary is shared by two projections: a place projection for the board district, whose geographic `covers` relation keeps its existing publication gate, and an organization projection for the public body that carries source-qualified members, meetings, committees, and recommendations. Community Board people use `community-board-person:{board_id}:{publisher_person_id|reviewed_local_id}` and temporal, provenance-bearing role edges; they never become Council `official:{PersonId}` identities or route to the Council official profile. The citywide **Community Boards** agency entry remains an index, not a replacement for the 59 board-level identities.
- **Materialization seam.** Builders under `tools/`, `warehouse/lib/`, and Worker refresh code create compact, versioned projections. Browser and edge reader routes use only those CityScroll-owned projections. A miss serves the latest-known-good materialization with its vintage or a deterministic unavailable/not-found result; it never triggers a synchronous publisher fallback. The generated data files are artifacts; their builders and checks are the authority.

## Runtime scenarios

**A visitor searches.** The browser loads the static shell and its ordered modules. A default lens reads committed or build-rendered data and may call a snapshot-only edge endpoint backed by a CityScroll-owned materialization. An explicitly invoked plain-English parse or translation is a separate transaction and can fail without invalidating the materialized record. Scope state travels in the route and is reused by Browse, Now, Near You, Following, maps, and record links. The pure scope adapter is [`site/scope_v0.mjs`](site/scope_v0.mjs).

**A visitor opens a record.** The Pages edge renders a source-backed document from static assets plus a Worker projection, and the browser adds supported process stages, entity links, location facts, actions, attachments, or related records. The resident can navigate to an official source-attribution URL. Missing evidence remains a named absence, and a failed acquisition is not cached as an empty fact.

The notice document is the one record path that still departs from the materialization rule, and it does so in a recorded, expiring way. `GET /notice` serves the D1 `notices` row when one exists — including a stale row, labelled rather than withheld — and only a missing binding, a missing row, or a failed D1 read reaches a single City Record query. No upstream row is an explicit not-found; a failed upstream read is an explicit unavailable. The Pages edge keeps its own City Record fallback for a Worker response it cannot use, and renders an unavailable document only when both fail. See the [departure register](architecture/no-live-external-debt.json) for the current call sites and expiries.

**The daily jobs run.** Three cron triggers are configured, and UTC is the authoritative clock for all of them. The `08:00 UTC` cron refreshes the sell-facing ZAP lookup, rematerializes Land outcomes from that lookup, and refreshes Land upcoming hearings and staffing exams so those reads do not wait behind the digest chain. The `10:00 UTC` cron performs the delivery-free digest shadow rehearsal. The `13:00 UTC` cron refreshes the D1 notice mirror, pre-warms prior-cycle data, rebuilds hearing and Property views, refreshes vendor projections and other read models, then evaluates alerts. With queue delivery enabled, one digest job is sent per subscription to the queue; the consumer retries independently and sends poison jobs to the dead-letter queue. Authenticated shadow repair POSTs enqueue a separate checkpointed rebuild and return `202`; each queue invocation evaluates one digest, records its result, and updates the reliability receipt after the run drains. The shadow-hold and send-cap rules are implemented in Worker code and documented in [`docs/architecture.md`](docs/architecture.md).

**A data build runs.** Host tooling ingests a bounded source or fixture into the warehouse, verifies counts and checksums, and exports a compact materialization. A builder writes the site artifact and, where needed, the Worker twin. Tests compare the pure producer and consumer contracts. The Worker request path consumes the result; it does not query DuckDB or Parquet directly.

**A join is proposed or published.** Entity-resolution code normalizes values and generates candidates. A scorer supplies evidence, a policy decides auto-link versus review versus separate, and a publication serializer removes desk-only fields. Cross-domain relation policy keeps uncertain candidates in shadow or evidence-only state. The relevant ADRs are [`docs/adr/entity-resolution-taxonomy.md`](docs/adr/entity-resolution-taxonomy.md), [`docs/adr/cross-domain-object-links.md`](docs/adr/cross-domain-object-links.md), and [`docs/adr/evidence-assertion-layer.md`](docs/adr/evidence-assertion-layer.md).

## Cross-cutting concepts

- **Provenance and evidence.** Values retain their publisher source, source URL where available, observed time, and derivation status. Public serializers expose only the allowed evidence and coarse confidence; raw snapshots, matcher scores, review identity, and desk notes stay private.
- **Honest missingness.** `null`, unavailable, not yet joined, and not published are different states. A projection may be empty because it found no qualifying rows, or unavailable because its source failed; readers must not collapse those cases.
- **Link-not-merge identity.** A canonical agency, vendor, official, project, parcel, or person can connect records without rewriting the records into one publisher object. Exact identifiers and conservative policies own the public edge; ambiguous text stays plain or evidence-only.
- **Dual-role civic identity.** A single publisher-backed `body_id` can anchor distinct place and organization projections when the source describes one stable civic body in both roles. Projection-specific relation families retain their own evidence gates: community-board geography is published only through the existing `covers` gate, while membership, meeting, and recommendation families require exact source identity, dates, retained documents, and observation receipts. Community Board staff, public committee members, and board members remain separate role semantics.
- **Materialization and freshness.** A read model has a producer, schema, timestamp or version, bounded scope, and failure behavior. Scheduled or manual acquisition determines freshness; resident and required-CI paths consume committed, generated, D1, KV, or R2 materializations without request-time publisher retrieval.
- **Privacy and spend limits.** Stateful features are rate-limited and capped. Four separate paths observe product use, and they are not one policy: a configured third-party session-analytics loader on the static site documents, which skips entirely on a browser opt-out signal; the first-party aggregate event dataset, which uses enumerated dimensions and no visitor identifier; private search-execution receipts; and a recognized account's own search history. Public `GET /stats` publishes served-coverage aggregates plus exactly two figures from those paths — searches run and searches returning records, for named periods — and nothing else about product use, delivery, or subscribers. The single inventory, including the facts this repository cannot establish about a third-party provider, is [`docs/collection-and-publication-boundary.md`](docs/collection-and-publication-boundary.md). LLM and email paths fail closed or degrade when their required configuration is absent.
- **Shared pure seams.** Browser and Worker implementations share small pure adapters for scopes, geography, process stages, relation policy, and read-model shapes. Tests protect parity at those seams instead of relying on one large runtime module.
- **Architecture as code.** This page is the human narrative; [`docs/architecture.md`](docs/architecture.md) is the canonical detailed reference for invariants. ADRs, source contracts, builder checks, and generated facts remain the machine-near records and should link to the canonical reference rather than duplicate it.

## Resident-surface rendering standard

This enforced standard protects plain-language and cognitive accessibility for residents. Its
canonical decision owner is recorded in the
[semantic-owner receipt](docs/repository-governance/semantic-owner-mapping.v1.json).

Resident-facing surfaces must not expose implementation-facing snake_case schema, column, or method
vocabulary, `Unavailable` debug rows, or reconciliation disclaimers in their default content.
Evidence and provenance may remain available through an explicit, user-invoked details affordance,
but internal field names and debug placeholders are not resident copy. The shared reader-label
adapter is [`site/reader_surface_labels.mjs`](site/reader_surface_labels.mjs), and shared edge
renderers consume it before producing visible labels.

The architectural fitness function is the fully enforced full-surface
[rendered schema-vocabulary census](test/standards/rendered_schema_vocabulary.py). It enumerates
the built documents plus route, tab, facet, scope, and detail states, and fails on any residual
vocabulary or default debug copy across that set—not only on pages changed by a patch. Changes to
resident renderers must keep this invariant and its full built-site sweep green.

## Home cold-load wire budget

This section records the current measured ceiling and its operational tradeoff. Its canonical
decision owner is recorded in the
[semantic-owner receipt](docs/repository-governance/semantic-owner-mapping.v1.json).

The `home.cold` `wireBytes` budget protects the weight of the first uncached visit to the home
surface, including the resources needed before the browser has a warm cache. Audience impact is
the operating assumption is that this budget protects NYC residents opening the site on
slow networks, lower-end mobile devices, or data-capped connections. The measurement is a
compressed-byte guard for page weight, not a claim about any particular resident's connection or
device.

A hard number and ratchet exist to make silent page-weight creep visible. Every new home-surface
dependency or user-facing card consumes part of a shared allowance, so adding it should be a
conscious trade rather than the default outcome of an otherwise successful feature merge. The
`460000`-byte ceiling is deliberately above the recorded measurement of about
`447729` bytes, leaving `12271` bytes of headroom at that observation. Those values and the
audience assumption are retained as the evidence basis for the current guard.

Loosening the ceiling has a real cost: a higher ceiling can make first paint slower on weak
connections and transfers more data on each uncached visit. Holding it too tightly has a
different cost: it can block useful user-facing features or encourage code contortions such as
deferring the Property feed, which removes required first-load content and breaks route and
accessibility contracts. The current posture is therefore a deliberate, reviewable ceiling with
explicit headroom, not permission for unbounded growth. The deeper optimization toward the old
`435000` aspiration remains a tracked follow-on, not an abandoned goal.

## Important decisions

- **Community boards as dual-role civic bodies.** Board identity is publisher-keyed by `body_id` and shared by place and organization projections. Geographic `covers` remains separately gated; source-qualified Community Board people and temporal roles are distinct from Council official identities and preserve board-local identity, role semantics, dates, and receipts. The aggregate Community Boards agency remains an index. The separate `recommendation` catalog object gives a publisher-keyed board output a stable target without conflating it with a meeting or matter; it remains unregistered and at grounding `gap` until the exact publisher identity, date, and retained source document are present. Rationale is recorded in [`docs/adr/ontology-registry-v0.md`](docs/adr/ontology-registry-v0.md).
- **Architecture facts are generated at verification time.** LA4's machine-owned evidence is generated in memory by [`tools/build_architecture_facts.mjs`](tools/build_architecture_facts.mjs) and checked against the C4 model and ADRs by [`tools/reconcile_architecture.mjs`](tools/reconcile_architecture.mjs). Pull-request, merge-group, and scheduled checks retain short-lived downloadable evidence; full `facts.json` is not committed. The facts record observed configuration and ontology counts, plus an `observer_coverage` block that names the paths the extractor parsed and the known-canary surfaces it still cannot see. The extractor first-class-observes production search collection families, the keyword-index builder, constellation producers and the PASSPort graph ceiling, Exams public-eligibility, Pages-edge routes/renderer, and the primary-document materializer. The canary list is human-owned data in [`architecture/observer-canaries.json`](architecture/observer-canaries.json); it is the single registration for observer coverage, the reconciliation workflow path filter, and the watermark. A listed path missing from that filter is a failing [`test/architecture_path_coverage.test.mjs`](test/architecture_path_coverage.test.mjs), not a silent gap. A non-empty `unmapped_surfaces` set is a first-class `unknown_surface` reconciliation outcome. The reviewed baseline is the versioned, stable-owner shard set under [`architecture/watermark.d/`](architecture/watermark.d/): one deterministic semantic-key file for observer coverage, each canary, ontology, bindings, and performance observability. The reconciler validates and derives the compact `cityscroll.architecture.watermark.v1` projection in memory, and writes that compatibility projection only to an explicit generated output directory. `--check` is healthy only when coverage is complete, topology is unchanged, and the derived reviewed baseline matches current observed reality. Duplicate owners or keys, missing or stale keys, malformed shards, and id/path mismatches fail closed; filenames never select a winner. That comparison is the architecture-reconciliation job, not a Unit-family assertion. Advancing a reviewed key requires `--write-watermark --watermark-key <semantic-key>` and changes only its owned shard; `--check` never updates source shards. They do not supply design rationale. Rationale: `rationale required`.
